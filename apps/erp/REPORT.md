# ShipYard 로컬 MVP 작업 보고서

## 작업 1 · 초기 조사

ShipYard 폴더는 비어 있었으며 Git 저장소나 프로젝트 지침이 없었다. Python 표준 라이브러리와 SQLite로 로컬 실행 환경을 구성한다. 모의 데이터는 국내 상선 신조 공정 순서를 예시로 사용한다.

## 작업 2 · 저장소와 API

기준일, 현재 예정일, 공정 실제일을 분리했다. 최초 가정으로 발행 시작일을 월요일로 제한하고, 84일 구간에 기준일이나 예정일이 걸리는 공정을 발행 시점에 복사한다. 발행 번호는 전체 순번이며 기존 발행본을 수정하는 API는 없다. 예정일이 기준일보다 늦으면 사유가 필요하다. 작업지시는 일일 작업을 같은 주간 지시에 연결하며, 모든 등록 주간 지시가 합격하면 가장 늦은 주간 작업 실제일을 공정 실제일로 기록한다.

블록 위치는 시작 전 확인 위치를 보관한다. 진행 중에는 이동 ID와 함께 이동 중 상태를 반환한다. 이동 확정과 블록 위치 변경은 한 트랜잭션으로 저장한다. 크레인 관측값은 이동 ID로 연결되며 위치 갱신에는 관여하지 않는다.

## 작업 3 · 작업 화면

계획, 작업지시·실적, 블록 이동, 기준정보를 브라우저에서 입력하고 조회할 수 있게 했다. 발행본은 접어 두고 필요한 버전만 펼쳐 확인할 수 있다. 등록된 기준정보를 선택 목록에 표시하고 입력 오류는 입력값을 유지한 채 화면에 표시한다.

## 작업 4 · 입력 검증과 재현 테스트

Python 표준 테스트 3건을 모두 통과했다. HTTP 요청 파싱부터 SQLite 저장 및 JSON 응답까지 임시 DB에서 실행했다.

- 12주 발행본에 6개 공정이 포함되고, 기준일이나 기존 발행본을 바꾸지 않고 최신 예정일을 갱신할 수 있다. 월요일이 아닌 시작일과 사유가 없는 예정 지연을 거절했다.
- 일일 검사 불합격 시 주간 합격을 거절하고, 일일 재검사 합격 후 주간 합격을 받아들였다. 지연 사유 없이 실적을 제출해 실패하면 작업 실적도 저장되지 않는다.
- 이동 중 텔레메트리만으로 블록 위치가 바뀌지 않으며, 장비 중복 사용과 이중 확정을 거절한다. 이동을 확정해야 목적지가 마지막 확인 위치가 된다. 초기 위치 미확인 블록도 이동을 시작할 수 있다.

JavaScript 구문 검사도 통과했다. 이 세션에서는 루프백 포트에 바인딩할 권한이 없어 실제 브라우저 조작 검증은 하지 못했다.

## 로컬 실행

ShipYard 폴더에서 Python 3.9 이상으로 실행한다. 첫 실행 시 같은 폴더에 SQLite 파일과 모의 데이터가 생성된다.

```sh
python3 -B app.py
```

브라우저에서 http://127.0.0.1:8000 을 연다. 예시 데이터에서 B101은 M1 이동 중이며 시작 전 마지막 확인 위치는 SHOP이다. 블록 이동 화면에서 M1의 텔레메트리를 추가해도 위치가 유지되며, M1을 확정하면 DOCK으로 바뀐다. B102의 초기 위치는 미확인이다. 다른 포트는 `--port 8001`로 지정할 수 있다. 빈 DB를 만들려면 새 파일 경로와 함께 `--empty --db local-empty.sqlite3`를 사용한다.

```sh
python3 -B -m unittest -v
```

## Unity 조회 계약

기본 주소는 `http://127.0.0.1:8000/api/`이고 조회는 GET으로 JSON 배열을 반환한다.

- `hulls`, `blocks`, `locations`는 호선·블록·시설 기준정보를 반환한다. 블록의 `location`은 마지막 확인 시설 ID이며, `position_status`는 `confirmed`, `in_transit`, `unknown` 중 하나다. 이동 중이면 `active_move`로 이동 작업을 찾는다. 호선 자체 좌표는 제공하지 않는다.
- `activities`, `plans`, `orders`는 현재 공정 날짜와 차이, 발행 당시 스냅샷, 작업지시별 실적을 반환한다. 차이는 기준일에 대한 달력 일수다.
- `moves`는 블록·장비와 출발지·목적지, 서버가 기록한 시작·확정 시각을 반환한다. `telemetry`의 `move`는 이동 ID이며 X/Y와 하중은 모의 m/t 값이다. 수신 시각을 UTC로 기록한다.
- `meta`는 화면에서 사용할 입력 필드와 공정 선택값을 반환한다.

## 남은 작업

회사별 계획 발행 승인과 확정 기간, 실적 완료 기준, 일정 수정 권한을 합의해야 한다. 현재 검사 재등록은 같은 작업지시의 최신 판정을 저장한다. 검사 이력과 이동 취소·정정, 사용자 권한 및 감사 이력은 후속 작업이다. 호선·시설 좌표와 센서 좌표계, 시간 및 장비 ID 매핑을 정의해야 Unity 시각화와 실장비 연동을 검증할 수 있다. 외부 배포는 수행하지 않았다.

## 작업 5 · 생산 현황과 호선별 조회

SAP Fiori Overview Page 패턴을 참고해 첫 화면에 예정 지연, 검사 불합격, 이동 중, 위치 미확인 건수를 배치했다. 각 카드는 예정일 갱신, 검사 등록, 이동 확정 등 해당 작업 화면으로 연결된다. 조회 호선 선택은 현황 집계와 공정·작업·블록·이동 목록 및 발행본 내역에 적용된다. 입력 폼의 기준정보 선택 범위는 전체이며 화면의 필터는 조회에만 적용된다.

공개 자료는 [SAP Fiori Overview Page](https://www.sap.com/design-system/fiori-design-web/v1-84/page-types/floorplans/overview-page), [HD한국조선해양 2023 통합보고서](https://esg.hd.com/upload/admin/report/1724202850245/%28ENG%29%202023%20HDKSOE_Integrated%20Report.pdf), [삼성중공업 SYARD 소개](https://www.samsungshi.com/En/Notice_news_view.aspx?no=74)를 참조했다. 운영 데이터와 회사별 세부 절차는 공개 자료에서 확인할 수 없어 기존 모의 규칙을 사용했다. JavaScript 구문 검사와 HTTP·SQLite 회귀 테스트 3건이 통과했다.

## 작업 6 · 호선·블록 상세, MRP, APS

- 기준정보에서 호선 ID와 호선명을 등록하고 선종, 선명, 선주, 전장, 폭, 인도 예정일을 저장한다. 블록 상세에는 구역, 조립 단계, 중량, 도면·리비전을 저장한다. 상세 편집 시 기존 값이 불러와진다. 치수와 중량은 소수점 셋째 자리까지 입력할 수 있다.
- 자재 소요계획은 현재고와 소요일까지 예정된 입고를 소요일 순서로 미완료 공정에 배분한다. 부족량과 소요일에서 조달기간을 뺀 발주 권고일을 계산한다. 수량은 정수이며, 부족분이 실제 구매발주를 생성하거나 이후 날짜로 이월되지는 않는다. 다단계 BOM, 구매·재고 거래 및 작업실적에 따른 재고 차감은 후속 범위다.
- 제약 일정은 등록된 단일 선행 공정, 최초 착수 가능일, 월~금 가동, 작업장의 일 가용시간과 작업시간을 반영한다. 같은 작업장에는 날짜별로 한 작업만 배정하며 하루 잔여 시간은 배분하지 않는다. 자재 부족과 선행 보류를 표시한다. 제안은 기존 예정일과 발행본을 변경하지 않는다. 다중 선후행, 교대·휴일·정비, 크레인/도크 자원 동시 제약, 늦은 입고에 맞춘 재일정은 후속 범위다.
- 조회 API는 `/api/vessel_details`, `/api/block_details`, `/api/mrp`, `/api/aps` 등을 제공한다. 기존 DB는 실행 시 테이블이 추가된다. 기존 DB에는 상세 예시가 자동 입력되지 않는다. 전체 예시는 새 파일 경로로 실행한다.
- 자동 테스트 4건과 JavaScript 구문 검사를 통과했다. 모의 강판 25장 소요에 현재고 20장을 적용해 5장 부족을 확인했다. 소요일에 5장 입고를 추가한 뒤 선후행과 작업장 중복 배정을 확인했다. 기존 예정일이 유지되고 상세값 수정 및 잘못된 치수 거절도 확인했다. 실제 브라우저 조작은 이번에도 검증하지 않았다.

```sh
python3 -B app.py --port 8001 --db planning-demo.sqlite3
```

## 작업 7 · 구매부터 생산 실적까지

호선 공정의 자재 소요 ID를 구매요청에 연결한다. 구매요청당 한 발주를 등록하며 발주는 공급업체와 납기 예정일을 가진다. 미입고 발주량은 MRP의 예정 공급으로 반영된다. 합격 입고만 현재고를 늘리고 발주 잔량을 줄인다. 불합격 입고는 이력에 기록하고 발주 잔량을 유지한다. 발주는 부분 입고를 허용한다.

출고는 소요 ID와 동일 공정의 주간 작업지시 ID를 함께 기록한다. 현재고와 미출고 소요를 넘는 출고를 거절한다. MRP는 출고된 수량을 소요에서 제거한다. 작업의 실제일 기준 공정 필수 자재가 모두 출고되어야 합격 실적을 등록할 수 있다. 한 공정에 여러 작업지시가 있으면 공정 기준 출고 누계를 공유한다. 거래 데이터와 재고 변경은 한 트랜잭션으로 처리한다.

검증은 기존 회귀를 포함해 5건 통과했다. 발주 후 MRP 부족 해소, 불합격 및 부분 입고, 초과 입고와 재고 부족 출고 거절, 출고 후 실적 확정을 임시 DB에서 검증했다. 실제 화면 클릭은 확인하지 않았다. 구매 승인, 발주 정정·취소, 창고·로트·예약, 품목별 BOM, 실사용량과 반납·폐기, 구매 대금 정산은 후속 범위다. 기존 수동 입고 예정과 구매 발주 잔량은 합산하므로 같은 공급을 양쪽에 중복 입력하지 않는다.

## 작업 8 · 로컬 주소 통합

로컬 기본 포트를 8001로 지정했다. 최신 구매·생산 예시를 실행할 때는 `python3 -B app.py --db procurement-demo.sqlite3`를 사용한다. 기본 DB로 실행할 때는 같은 주소에서 `python3 -B app.py`를 사용한다. 이전 예시 및 기본 DB 파일은 보존한다.

## 작업 9 · 시설, 워크센터, 창고별 출고

시설 기준정보에 야드와 창고를 추가했다. APS 작업장의 가용시간과 시설의 물리적 위치는 워크센터별 시설 연결로 관리한다. 입고 시 창고를 지정하며, 합격 입고는 품목 총재고와 창고별 재고를 함께 증가시킨다. 기존 총재고는 미배정 수량 범위에서 창고에 배정한다.

출고는 출발 창고 재고를 검증하고 공정의 APS 작업장에 연결된 시설을 도착지로 저장한다. 총재고와 창고 재고 차감 및 출고 이력은 한 트랜잭션에 저장된다. MRP는 총재고를 사용하며 창고별 공급 우선순위와 이동 리드타임은 아직 적용하지 않는다. 생산 시설의 수령 확인이나 현장 보관 재고는 후속 범위다.

## 작업 10 · PostgreSQL 전환

Docker Compose의 PostgreSQL 17과 Python psycopg를 연결했다. 브라우저와 Unity API 주소는 8001이고 DB는 로컬 55432에서만 수신한다. 비밀번호는 Git에서 제외된 로컬 `.env`에 있고 DB 데이터는 Docker 볼륨에 저장된다.

8001 서버의 쓰기를 중지하고 `procurement-demo.sqlite3`를 읽기 전용으로 열어 참조 무결성을 확인했다. 25개 테이블의 30개 행을 한 트랜잭션으로 복사해 각 행의 열 값과 개수를 대조했고, 계획·텔레메트리 자동 ID를 이어서 발급하도록 재설정했다. 원본 파일은 보존했다. 다른 SQLite 예시 파일은 이번 이전 범위에 포함하지 않았다. 전환 후 8001에서 강판 5장 부족과 후판 창고 재고 20장을 조회했다.

SQLite와 PostgreSQL 각각 자동 테스트 6건이 통과했다. 각 PostgreSQL 테스트는 별도 스키마를 만들고 종료 시 삭제한다. 재고 20장에 15장 출고 두 건을 동시에 요청하면 1건만 성공하고 품목 및 창고 잔액이 모두 5장이며 출고 이력은 1건이다. 여러 테이블에 걸친 업무 규칙을 유지하기 위해 현재 API의 쓰기 트랜잭션은 PostgreSQL 트랜잭션 잠금으로 직렬화한다. 운영 부하에 맞춘 품목·창고 단위 잠금, 연결 풀, 역할 권한과 백업·복구 시험은 후속 작업이다.

같은 Mac에서 재시작할 때는 ShipYard 폴더에서 실행한다. 기존 DB 볼륨을 삭제하면 저장 데이터도 삭제된다.

```sh
docker compose -p shipyard up -d --wait
./shipyard-postgres app.py
```

개발 환경 최초 구성에는 `python3 -m venv .venv`, `.venv/bin/pip install -r requirements.txt`와 `SHIPYARD_DB_PASSWORD`를 지정한 로컬 `.env`가 필요하다(`cp .env.example .env` 후 값 변경). 이미 초기화된 볼륨의 비밀번호는 DB 계정과 일치해야 한다.

## 작업 11 · 업무 흐름, 문서 채번, 수불과 역추적

생산 현황에 계획 발행부터 실적 등록까지 업무 바로가기를 추가했다. 기준정보에는 호선·블록·시설·워크센터·장비·품목·공급업체를 모았다. MRP 부족 행에서 구매요청을 열면 소요 ID와 부족 수량을 채우며, 구매요청에서 발주로, 발주에서 입고로 이어갈 수 있다. 발행본에서 작업지시를 생성하면 원래 계획 버전이 저장되고, 일일 지시는 상위 주간 지시의 계획 연결을 상속한다.

계획에는 PLAN 번호를 표시하고 공정·소요·작업지시·구매요청·발주·입고·출고·이동의 신규 입력은 서버에서 자동 채번한다. 각 실적과 재검사를 별도 RES 문서로 저장하고 기존 작업지시의 최신 판정도 갱신한다. 기존 문서 ID를 보존한다. 업그레이드 시 기존 실적은 당시의 최신 기록만 이관할 수 있으며 원래 기록 시각은 비워 둔다. 이전 작업지시와 발행본 연결은 추정해서 채우지 않는다.

창고 수불부는 기초 배정, 합격 입고, 출고를 원천 문서와 연결하고 수불 수량과 기록 순서 기준 처리 후 잔량을 보여준다. 품목과 창고별로 조회할 수 있다. 이전 시점의 창고 잔액을 기초로 올리고 기존 입고·출고 문서는 기존 이력으로 조회한다. 기초 이전 거래를 수불부에 소급 재작성하지 않는다. 문서 추적은 공정·품목 연결 자료를 함께 표시한다. 현재 품목·창고 단위로 추적하며 입고 로트나 강판 히트번호를 특정 블록의 실제 사용분에 연결하는 기능, 반납·이송·조정·역분개는 후속 범위다.

SQLite와 PostgreSQL에서 각각 자동 테스트 7건을 통과했다. 자동 채번, 발행본 연결과 상속, 재검사 이력 보존, 부분 입고와 출고 후 장부 잔량을 확인했다. 8001번 화면에서 MRP 부족 수량 5장이 구매요청 폼에 채워지고 수불 장부에서 공정·계획 문서가 열리는 것을 확인했다.

## 작업 12 · 업무 홈, 목록, 문서 상세 분리

SAP Fiori의 [List Report와 Object Page](https://help.sap.com/docs/SAPUI5/b2f662dd9d7a4ec680056733050b4d34/c0eec49db81a441e878f528c8f3d28de.html)를 참고해 검색·상태 필터가 있는 목록을 기본 화면으로 두고 문서 상세와 등록 창을 분리했다. [더존 ERP 모듈 구성](https://www.douzone.com/business/extended_erp.jsp)을 참고해 계획·실행·기준정보 메뉴를 구성했다. [영림원 K-System Ace의 프로세스 기반 구성](https://www.ksystem.co.kr/k-system-ace/)을 참고해 실제 데이터에서 계산한 처리 대기 목록과 문서별 다음 작업을 메뉴와 별도로 제공한다.

생산 준비와 자재 준비를 병렬 업무로 제시하고, 작업지시와 가용 재고가 출고에서 만나는 흐름을 표시한다. 구매요청 대기, 발주 잔량, 재검사, 이동 확정 등 실제 데이터에 근거한 항목을 업무 홈에 표시한다. 대기 상태는 현재 데이터로 계산한 것이며 결재나 담당자 배정 상태는 아니다. 공개 제품 자료의 설계 패턴을 참고했으며 제품 내부 화면이나 고객사 설정은 확인하지 않았다.

8001번 브라우저에서 실제 부족량 5장, 구매요청 창의 소요 ID와 수량 자동 입력, 목록과 등록 창 분리, MRP 상태 필터, 소요 문서 상세와 계획 링크를 확인했다. 시험 중 구매요청을 저장하지 않았다. 기존 API 테스트 7건과 JavaScript 구문 검사를 통과했다.

## 작업 13 · 시각적 업무 안내

밝은 배경과 청록색 강조로 메뉴, 목록, 입력 창의 스타일을 통일했다. 업무 홈에서 자재 부족·미입고 발주·미완료 작업 건수를 누르면 해당 목록으로 이동한다. 생산 준비와 자재 준비를 두 카드로 배치하고, 현장 실행 카드에서 작업지시와 가용 재고가 출고·실적으로 이어지는 관계를 화살표와 그림문자로 표현했다. 사진은 사용하지 않았으며 공정 이해를 돕는 도식과 그림문자를 사용했다. JavaScript 구문 검사와 8001번 브라우저의 홈 화면 배치 확인을 완료했다.

## 작업 14 · 생산관리 메뉴 점검과 조회 표준화

기존 메뉴에서 공정별 진척과 착수 준비, 품질 검사 전용 조회가 부족했다. 생산 진척 메뉴에는 계획·실제일 차이를 가진 공정 목록과 주간 지시별 준비 조회를 추가했다. 준비 조회는 계획 발행본 연결, 작업 시설, 공정 기준 미출고 수량을 보여준다. 품질 검사 메뉴는 작업 검사와 입고 검사를 별도 탭으로 제공하고 기존 실적·검수 원천 문서를 사용한다. 상태는 등록 데이터에 근거한 조회이며 작업 착수 승인 기능은 아니다.

모든 목록에 검색, 상태, 적용 가능한 자재·창고·기간, 정렬 기준과 방향, 조건 초기화, 20건 단위 페이지 이동을 적용했다. 숫자는 숫자 크기로 정렬한다. 탭별 조회 조건과 마지막 탭은 페이지가 열린 동안 유지된다. 탭에는 선택 상태와 키보드 좌우 이동을 적용했다. 수불 잔량은 처리 당시 잔량이므로 조회 정렬을 바꿔도 재계산하지 않는다.

8001번 브라우저에서 공정·착수 준비 탭, 원천 데이터에서 계산한 준비 상태, 검색 결과 없음과 조건 초기화, 작업·입고 검사 탭을 직접 확인했다. JavaScript 구문 검사 통과.

현재 메뉴는 초기 구매·자재·생산 실행과 추적 범위를 제공한다. 운영형 생산관리 전체 범위에서는 다단계 BOM과 설계 변경, 부분 생산 수량·공수, 교대·휴일 달력, 불량 원인·재작업 지시, 로트/히트번호, 자재 반납·이송·역분개, 승인·마감·권한이 남는다. 이번 변경은 이 미구현 업무를 수행한 것으로 표시하지 않는다.

## 작업 15 · 조선소 주요 일정과 블록 준비

호선·블록 계획 메뉴를 추가했다. 착공·기공·진수·시운전·인도는 기준일과 최신 예정일을 따로 등록한다. 일정 변경·실적 등록 시 사유와 시각을 별도 문서로 남기고 기준일을 보존한다. 블록 구성은 상위/구성 블록을 연결하며 한 구성 블록의 부모는 하나다. 탑재 선후행은 여러 선행 블록을 허용하고 다른 호선 연결 및 순환 관계를 거절한다.

블록별 탑재 계획에 기준일·예정일·시설을 등록한다. 준비 현황은 도면 출도, 자재 준비, 조립·의장·도장 완료, 검사 승인, 시설 확보, 이동 준비의 확인 근거를 이력으로 남긴다. 최신 확인 외에도 미출고 자재와 탑재 전 공정의 실제 완료, 구성 블록 조립, 선행 블록의 계획 시설로 확정된 이동을 검사한다. 탑재 공정 자체의 완료는 탑재 준비 선결조건에 포함하지 않는다. 과거 확인 이력은 보존하고 새 판정으로 갱신한다.

SQLite·PostgreSQL에서 각각 테스트 8건을 통과했다. 일정 변경 사유, 기준일 보존, 순환·다른 호선 연결 거절, 확인 입력 후에도 미완료 선행 조건에 의해 보류되는 상태를 검증했다. 8001 브라우저에서 일곱 탭과 B101 준비 미확인·자재 부족·미완료 사유 표시를 확인했다.

초기 가정으로 주요 일정 종류와 준비 항목을 고정했다. 일정 날짜만으로 다른 계획을 자동 재배치하지 않는다. 도크 점유 예약, 선행 블록의 실제 탑재 검사 증명, 작업장 자원 자동 확보는 후속 범위다. 현재 선행 탑재 판단은 등록된 계획 목적지로 이동 확정된 기록을 사용하는 모의 규칙이다. 기존 운영 데이터에 주요 일정이나 확인 완료를 임의로 입력하지 않았다.

## 작업 16 · SN2036 가상 호선

실행 중인 PostgreSQL에 SN2036 174K LNG 운반선 시나리오를 추가했다. 가상의 선명·선주와 작업 데이터이며 기존 H101과 함께 조회할 수 있다. 주요 일정 5건, 블록 5개, 공정 6건, 구성·탑재 선후행, 12주 발행본, 주간 지시, 후판 소요·발주·부분 입고를 연결했다. 초기 후판 36장 중 8장 추가 입고, 발주 8장 미입고 상황을 재현했다. 스크립트는 같은 호선을 중복 등록하지 않는다.

## 작업 17 · 조선 생산 프로세스 적합성 보완

조선소 생산 흐름과 비교해 부족했던 항목을 구현했다.

- **블록 조립 단계와 공수**(`production.py`): 블록별 절단·가공 → 소조립 → 중조립 → 대조립 → PE → 탑재 단계, 계획 공수, 누적 진척률 실적, 사내협력사. 앞 단계와 구성 블록이 끝나야 단계를 완료하고, 탑재 단계는 탑재 검사 합격이 필요하다. 블록·호선별 중량 기준 및 공수 기준 진척률, 생산성(기성/투입), 협력사별 공수를 조회한다.
- **도크·크레인 제약**(`resources.py`): 장비 정격하중·배치 시설, 도크 점유 예약(중복 거절), 휴일 달력, APS 다중 선행 공정(순환 거절). 블록 이동 시 중량이 장비 정격하중을 넘으면 거절한다. 탑재 일정 제안은 선행 블록, 크레인 용량, 크레인당 하루 1회 인양, 휴일, 도크 예약 범위를 반영한다.
- **강재 추적**(`lots.py`): 합격 입고의 로트(히트번호·밀시트), 출고별 로트 배정(같은 자재·같은 창고·잔량 검사), 반납·잔재(재고·수불부 복원)와 폐기, 블록별 강재 추적, 구성 블록을 포함한 블록 트리 자재 소요.
- **의장품**: 선행/후행 의장품, 입고 → 설치 → 검사 완료 순서 강제. 선행의장품 미설치는 탑재 준비를 막는다.
- **품질**(`quality.py`): ITP(사내·선주·선급 입회), 입회 검사 실적, 불합격 시 NCR 자동 발행, 재검사 합격 후 NCR 종결, A·B·C 등급 펀치리스트.
- **주요 일정 게이트**: 기공(첫 블록 탑재 합격), 진수(계획 블록 전부 탑재), 시운전(의장품 검사 완료·A 펀치 종결), 인도(추가로 미결 NCR 없음·A/B 펀치 종결·ITP 전부 합격).
- **설계 변경**: 도면 리비전과 설계 변경 이력. 최신 리비전 이후 ‘도면 출도’ 재확인이 없으면 탑재 준비를 막는다.
- **선행 블록 탑재 판정**: 기존의 “계획 시설로 이동 확정” 모의 규칙을 탑재 검사 실적(합격 기록)으로 바꿨다. 합격 기록은 블록이 그 시설로 이동 확정되었고 준비 현황이 ‘준비 확인’일 때만 저장된다.
- **권한과 감사**(`governance.py`): 관리자·계획·생산·구매·품질·조회 역할별 저장 권한, 모든 저장 요청의 감사 이력. 첫 사용자는 관리자여야 하고, 사용자가 없으면 기존처럼 권한 검사 없이 동작한다. 작업자는 `X-ShipYard-User` 헤더로 전달하며 비밀번호 인증은 없다.

신규 테이블은 기존 스키마에 추가만 하며, 서버 시작 시 `CREATE TABLE IF NOT EXISTS`로 생성된다. 기존 테이블 구조와 데이터는 바꾸지 않았다. 다만 판정 규칙이 엄격해져 기존 데이터의 탑재 준비 현황에 ‘도크 점유 예약 없음’, ‘탑재 크레인 미배정’ 사유가 새로 나타날 수 있다.

SQLite와 PostgreSQL에서 각각 자동 테스트 15건(기존 8 + 신규 7)이 통과했다. 헤드리스 Chrome으로 전체 메뉴·탭을 열고 등록 창을 열어 스크립트 오류가 없음을 확인했으며, 화면에서 NCR 종결 거절, 첫 관리자 등록, 작업자 미선택 저장 거절을 확인했다. `seed_production.py`는 SN2036에 예시를 추가한다(임시 SQLite에서 검증, 운영 DB에는 실행하지 않음).

남은 범위: 네스팅(절단 배치) 최적화와 잔재 형상 관리, 교대 근무·작업장 일부 시간 배분, 로그인 인증, 대금 정산.

## 작업 18 · 로그인, 그룹별 메뉴 권한, Redis 세션과 조회 최적화

- **로그인·회원 관리**(`auth.py`): 계정(`accounts`), 그룹(`user_groups`), 그룹×메뉴 조회/등록 권한(`group_permissions`), 로그인 이력(`login_events`). 비밀번호는 PBKDF2-HMAC-SHA256(60만 회, 사용자별 salt)로 저장한다. 정책은 8~128자, 문자+숫자, 아이디와 다름이다. 첫 관리자는 `create_admin.py`로 만든다. 이전 작업의 `X-ShipYard-User` 작업자 선택과 고정 역할(`governance.py`, `users` 테이블)은 제거했고, 역할은 기본 그룹(PLAN·PROD·PURCH·QA·VIEW)으로 옮겼다. 기존 DB의 `users` 테이블은 더 이상 사용하지 않는다.
- **메뉴 권한**(`menus.py`): 메뉴·탭·저장 작업 정의를 서버로 옮겨 화면과 공유한다. 메뉴 조회 권한은 그 메뉴의 목록과 의존 목록(호선 범위·상태 표시·입력 선택지)을, 등록 권한은 그 메뉴의 저장 작업을 허용한다. 서버가 모든 조회·저장을 이 기준으로 검사한다.
- **Redis 토큰**: 로그인 시 256비트 무작위 토큰을 `Authorization: Bearer`로 전달한다. Redis에는 토큰의 SHA-256만 저장한다. 사용할 때마다 8시간씩 연장되고, 사용자별 세션 집합으로 비밀번호 변경·초기화·계정 중지 시 즉시 폐기한다. 로그인 실패는 계정별로 세어 5회면 15분간 잠근다. 브라우저는 토큰을 sessionStorage에 둔다(탭을 닫으면 종료).
- **조회 최적화**(`cache.py`, `search.py`): 조회 결과를 `cache:<데이터 버전>:<경로>`로 Redis에 캐시(10분)한다. 저장 커밋 뒤 버전을 올려 이전 캐시는 다시 쓰지 않는다. 버전을 계산 전에 읽으므로 동시 저장과 경합해도 오래된 값이 새 버전에 저장되지 않는다. 시드·이관·관리자 생성 스크립트도 버전을 올린다. 화면은 연 메뉴에 필요한 목록만 불러오고, 긴 이력 6종은 서버 검색·정렬·페이지(검색 결과도 캐시)로 바꿨다. Redis 장애 시 조회는 캐시 없이 계산하고, 로그인·인증은 503을 반환한다.
- **구성**: `compose.yaml`에 Redis(`127.0.0.1:56379`, 비밀번호, AOF, 256MB `volatile-lru`), `requirements.txt`에 `redis`를 추가했다. PostgreSQL 모드는 `SHIPYARD_REDIS_URL`이 필수이고, SQLite 실행과 테스트는 메모리 저장소로 대체된다.

측정(PostgreSQL 임시 스키마, H101·SN2036·트윈 3척·확장 예시 데이터, 같은 Mac):

| 항목 | 변경 전 | 변경 후 |
|---|---|---|
| 화면 첫 로딩 요청 | 60건 · 534 KiB · 약 560 ms | 17건 · 60 KiB · 179 ms(캐시 없음) / 27 ms(캐시 적중) |
| 블록 준비 현황 | 약 190 ms | 첫 계산 176 ms, 이후 2 ms |
| 장비 관측 20건 페이지 | 전체 2,236건(약 330 KB) 전송 | 약 3 KB, 캐시 적중 시 2 ms |

SQLite(메모리 저장소)와 PostgreSQL+Redis에서 각각 테스트 17건이 통과했다. 새 테스트는 로그인·잠금·토큰 폐기, 그룹 메뉴 권한, 캐시 무효화와 서버 검색이다. 헤드리스 Chrome에서 로그인 실패·성공, 관리자의 메뉴 69개 탭 탐색(오류 0), 그룹·권한·사용자 생성, 제한 그룹 사용자의 메뉴 노출과 등록 버튼 숨김, 서버 검색을 확인했다. 운영 DB에는 실행하지 않았다.

남은 범위: HTTPS 종단, 비밀번호 찾기·다중 인증, 호선별 데이터 접근 제한, 블록 준비 현황 첫 계산의 쿼리 최적화(N+1).

## 작업 19 · Swagger API 문서

`openapi.py`가 서버 정의(조회 경로, 저장 작업 필드, 선택값, 필수 여부, 자동 채번, 메뉴, 검색 조건)에서 OpenAPI 3.0.3 문서를 생성한다. `GET /api/openapi.json`으로 제공하고, `GET /docs`에서 Swagger UI(jsDelivr의 swagger-ui-dist 5.17.14)를 연다. 보안 방식은 Bearer 토큰이다. Swagger에서 `POST /api/login`을 실행하면 응답 토큰이 Authorize에 자동으로 설정된다. 문서와 화면은 로그인 없이 볼 수 있지만 실제 호출에는 권한 검사가 그대로 적용된다.

openapi-spec-validator로 규격 검증을 통과했다(경로 77개, 작업 125개, 태그 19개). 헤드리스 Chrome의 Swagger UI에서 로그인 전 `/api/me` 401, 로그인 200과 토큰 자동 설정, 이후 `/api/me` 200을 확인했다. 자동 테스트 18건(문서 생성 포함)이 통과했다.
